## What Do These Words Actually Mean?

| Term | Meaning | Example |
|---|---|---|
| **Viewport** | The 3D window where you see and navigate the level | Where you fly the camera around |
| **Outliner** | The panel listing every actor currently placed in the level | Like a file list, but for objects in the scene |
| **Content Browser** | The panel for browsing assets — meshes, materials, blueprints — stored in the project | Where you'd find a cube mesh to place |
| **Actor** | Anything that can be placed in a level — a mesh, a light, a player start, an empty marker | Roughly Unreal's equivalent of an object instance |
| **Transform** | An actor's position, rotation, and scale together | Similar to `(x, y)` position in Pygame, but in 3D with rotation and scale added |
| **Editor Script Plugin** | The plugin that turns on Python scripting inside the Unreal Editor | Must be enabled before any of this unit's code works |
| **`unreal` module** | The Python module, available only inside Unreal, that gives scripts access to the editor | `import unreal` |
| **`EditorActorSubsystem`** | The object Unreal gives you to spawn, find, and manipulate actors from Python | `unreal.get_editor_subsystem(unreal.EditorActorSubsystem)` |

## Key Vocabulary

| Term | What it means |
|---|---|
| `unreal.EditorActorSubsystem` | The main entry point for spawning/finding/deleting actors via Python |
| `spawn_actor_from_class(class, location)` | Creates a new actor of the given type at a given position |

## Checkpoint 2 — Turning On Python & Your First Script 🐍

### 📋 Your Task

With the editor no longer unfamiliar, it's time to turn on Python. This checkpoint enables the plugin that makes it possible, and gets you from "typing a command in Unreal's own console" to "running a saved `.py` file that does something to the level."

### 🧠 Understand It First

Do these steps directly inside your Unreal project from Checkpoint 1.

**Block 1 — Enabling the Python Editor Script Plugin:**

Unreal doesn't have Python scripting turned on by default — it's a plugin you enable once per project. As you go through this, notice that Unreal asks to restart the editor afterward; this is normal, and expected every time a plugin's enabled state changes.

```
In the Unreal Editor:
1. Edit menu → Plugins
2. Search for "Python Editor Script Plugin"
3. Check the box to enable it
4. Click "Restart Now" when prompted
```

After restarting, look for a new panel or tab called **Output Log** — this is where Python commands can be typed directly and their results shown immediately, similar to a Python shell.

**Block 2 — Running your first commands directly in the console:**

Before writing a saved script, type these one at a time directly into the Output Log's Python input field, pressing Enter after each. As you go, notice that `unreal` is a module that ONLY exists inside this environment — trying `import unreal` in a normal terminal outside Unreal would fail.

**Block 3 — Listing every actor currently in your level:**

## Checkpoint 3 — Scripting Actors & Automating Editor Tasks 🏗️

### 📋 Your Task

Checkpoint 2 only read information out of the level. This checkpoint writes to it — spawning new actors and adjusting existing ones through code instead of dragging and dropping. The goal is to feel, concretely, why "automate it with Python" beats "do it by hand" the moment you need to place or adjust more than a couple of objects.

### 🧠 Understand It First

**Block 1 — Spawning a single actor via Python:**

Instead of dragging a shape from the Content Browser, this spawns one directly at a specific 3D position. As you run it, compare the result to what you'd have done manually in Checkpoint 1 — same outcome, completely different process.

```python

actor_subsystem = unreal.get_editor_subsystem(unreal.EditorActorSubsystem)

# Spawn a basic cube (StaticMeshActor) at position (0, 0, 100)
location = unreal.Vector(0, 0, 100)
new_actor = actor_subsystem.spawn_actor_from_class(unreal.StaticMeshActor, location)
new_actor.set_actor_label("MyFirstScriptedActor")

print(f"Spawned actor at {new_actor.get_actor_location()}")
```

**Block 2 — Batch spawning: a grid of actors in one script run:**

This spawns nine actors in a 3x3 grid — the kind of task that would mean placing and precisely nudging nine separate objects by hand. As you run it, time how long it takes versus how long you'd estimate the same layout would take manually in the viewport.

```python
import unreal

actor_subsystem = unreal.get_editor_subsystem(unreal.EditorActorSubsystem)
spacing = 200   # Unreal units between each spawned actor

for row in range(3):
    for col in range(3):
        location = unreal.Vector(col * spacing, row * spacing, 0)
        actor = actor_subsystem.spawn_actor_from_class(unreal.StaticMeshActor, location)
        actor.set_actor_label(f"GridActor_{row}_{col}")

print("Spawned a 3x3 grid of actors")
```

**Block 3 — Batch-editing EXISTING actors, not just spawning new ones:**

Automation isn't only about creating things — it's also about adjusting many things at once without touching each one by hand. As you run this, notice the filtering step (`if "GridActor" in ...`) — this script only touches actors matching a pattern, leaving everything else in the level untouched.

```python
import unreal

actor_subsystem = unreal.get_editor_subsystem(unreal.EditorActorSubsystem)
all_actors = actor_subsystem.get_all_level_actors()

for actor in all_actors:
    label = actor.get_actor_label()
    if "GridActor" in label:
        current_location = actor.get_actor_location()
        # Raise every matching actor up by 50 units, leaving X and Y unchanged
        new_location = unreal.Vector(current_location.x, current_location.y, current_location.z + 50)
        actor.set_actor_location(new_location, False, None)
        print(f"Raised {label} to {new_location}")
```

## Checkpoint 4 — Porting the Kingdom into 3D 🏰

### 📋 Your Task

This is where the year comes together. Unit 3's `generate_rooms()` produces a list of rectangles describing a recursively-generated labyrinth — as plain data, with no visual form at all. This checkpoint takes that exact same list and uses it to spawn a real 3D layout in Unreal: one floor actor per generated room, positioned and sized directly from the rectangle's own numbers.

### 🧠 Understand It First

**Block 1 — Recalling what `generate_rooms()` actually returns:**

Before touching Unreal, run this in a NORMAL Python terminal (not Unreal's console) to refresh what the data looks like. As you look at the output, notice it's just a list of `(x, y, width, height)` tuples — nothing about it is Unreal-specific yet.

```python

from algorithms import generate_rooms

rooms = generate_rooms(0, 0, 40, 30)
print(f"Generated {len(rooms)} rooms")
for room in rooms[:3]:
    print(room)   # each one is (x, y, width, height)
```

**Block 2 — Turning ONE rectangle into ONE floor actor:**

This is the core translation step — a single `(x, y, width, height)` tuple becomes a single scaled, positioned `StaticMeshActor` inside Unreal. As you read it, notice that `width` and `height` (2D concepts from Unit 3) become the X and Y **scale** of a 3D actor, while a fixed small value handles the actor's height (Z) — the labyrinth was never 3D to begin with, so a sensible height has to be decided, not read from the data.

```python
# Run this INSIDE Unreal's Python console

import unreal

def spawn_room_floor(x, y, width, height, actor_subsystem):
    # Position the floor at the CENTER of the rectangle, not its corner
    center_x = (x + width / 2) * 100    # scaled up — Unreal units are much larger than grid cells
    center_y = (y + height / 2) * 100
    location = unreal.Vector(center_x, center_y, 0)

    floor = actor_subsystem.spawn_actor_from_class(unreal.StaticMeshActor, location)
    floor.set_actor_scale3d(unreal.Vector(width, height, 0.1))   # flat, wide, matching the room's size
    floor.set_actor_label(f"Room_{x}_{y}")
    return floor

actor_subsystem = unreal.get_editor_subsystem(unreal.EditorActorSubsystem)
spawn_room_floor(0, 0, 8, 6, actor_subsystem)   # test with ONE room first
```

**Block 3 — The full labyrinth: looping over EVERY room, plus marking start and Minotaur:**

Now the two ideas combine: `generate_rooms()`'s output drives a loop that spawns one floor per room, and the first and last rooms get special markers — a player start and a Minotaur placeholder — using the exact recursive structure Unit 3 already built. As you read this, notice that not a single coordinate is typed by hand anywhere in this script; every position comes from the data.

```python
# Run this INSIDE Unreal's Python console, with algorithms.py accessible

import unreal
from algorithms import generate_rooms

def build_labyrinth(rooms):
    actor_subsystem = unreal.get_editor_subsystem(unreal.EditorActorSubsystem)

    for x, y, width, height in rooms:
        spawn_room_floor(x, y, width, height, actor_subsystem)

    # First room = player start; last room = the Minotaur's chamber
    start_x, start_y, start_w, start_h = rooms[0]
    minotaur_x, minotaur_y, minotaur_w, minotaur_h = rooms[-1]

    start_location = unreal.Vector((start_x + start_w / 2) * 100, (start_y + start_h / 2) * 100, 100)
    minotaur_location = unreal.Vector((minotaur_x + minotaur_w / 2) * 100, (minotaur_y + minotaur_h / 2) * 100, 100)

    player_start = actor_subsystem.spawn_actor_from_class(unreal.PlayerStart, start_location)
    minotaur_marker = actor_subsystem.spawn_actor_from_class(unreal.StaticMeshActor, minotaur_location)
    minotaur_marker.set_actor_label("MinotaurSpawnPoint")

    print(f"Built a {len(rooms)}-room labyrinth from pure recursion, top to bottom, no manual placement")

rooms = generate_rooms(0, 0, 40, 30)
build_labyrinth(rooms)
```

### 💡 Hints

**Why multiply by `100` when converting grid coordinates to Unreal positions?**

Unit 3's grid used small numbers (a `40 x 30` grid, say) representing abstract cells, not real-world distances. Unreal's default unit is roughly 1 centimeter, so placing rooms directly at their raw grid coordinates would squash an entire labyrinth into less space than a single character occupies. Scaling up (by 100, or whatever multiplier looks right once you see it in the viewport) is a deliberate, adjustable translation step — not a fixed rule.

**If your floors don't line up or overlap oddly:** double check you're computing the CENTER of each rectangle (`x + width/2`), not its corner (`x`) — a floor positioned at a rectangle's corner will be offset from where you'd expect it, especially for larger rooms.

**Bringing `algorithms.py` into Unreal's Python environment:**

Unreal's Python needs to be able to find your `algorithms.py` file. The simplest approach: copy `algorithms.py` into your Unreal project's Python scripts folder (the same one from Checkpoint 2) so `from algorithms import generate_rooms` can find it without any extra path configuration.

**Segment 3 (Python + Blueprint bridge) — Exposing `find_path` to Blueprint, so the Minotaur can actually hunt:**

This is the key idea of the whole checkpoint. Unreal lets a Python function be exposed so a Blueprint graph can call it directly, using `@unreal.ufunction`. As you read this, notice that the Minotaur's "brain" (which cell to move to next) is still 100% the recursive backtracking algorithm from Unit 3 — only now it runs once per game tick instead of once per turn in a text-based sandbox.

```python
# minotaur_ai.py — exposes Unit 3's find_path to Blueprint

import unreal
from algorithms import find_path   # the EXACT SAME function from Unit 3, unmodified

CELL_SIZE = 100   # must match the scale used in build_labyrinth (Checkpoint 4)

# A module-level grid, set once after the labyrinth is generated (see rooms_to_grid below)
CURRENT_GRID = None

def set_grid(grid):
    global CURRENT_GRID
    CURRENT_GRID = grid

def world_to_grid(location):
    return (int(location.y // CELL_SIZE), int(location.x // CELL_SIZE))

def grid_to_world(row, col, z):
    return unreal.Vector(col * CELL_SIZE + CELL_SIZE / 2, row * CELL_SIZE + CELL_SIZE / 2, z)

@unreal.uclass()
class MinotaurAI(unreal.BlueprintFunctionLibrary):
    @unreal.ufunction(static=True, params=[unreal.Vector, unreal.Vector], ret=unreal.Vector,
                       meta=dict(Category="MinotaurAI"))
    def get_next_step(minotaur_location, player_location):
        if CURRENT_GRID is None:
            return minotaur_location   # no grid set yet — stay put

        start = world_to_grid(minotaur_location)
        target = world_to_grid(player_location)
        path = find_path(CURRENT_GRID, start, target)

        if path is not None and len(path) > 1:
            next_row, next_col = path[1]   # path[0] is where the Minotaur already is
            return grid_to_world(next_row, next_col, minotaur_location.z)
        return minotaur_location   # no path found — stay put
```

Once this script has been run inside Unreal, a NEW node — **"MinotaurAI → Get Next Step"** — becomes available directly inside Blueprint's graph, exactly like any built-in Unreal node.

```
In your Minotaur Blueprint's Event Graph:
1. Event Tick → (Delay 0.5 seconds, so it doesn't recalculate every single frame)
2. Call "Get Next Step", plugging in Self's location and the player Character's location
3. Feed the returned Vector into "Set Actor Location" (or "Move To Location"
   over time, for smoother motion)
```

Recall Unit 3 and Unit 4's discussion of why a CACHED path doesn't help a moving target — this is the exact same idea, now running live: the Minotaur asks the question fresh, every half-second, because the player has moved since the last time it asked.

## Final Project — The Endless Labyrinth ♾️🏰

Bring the entire unit — and, in a real sense, the entire year — together into one playable, escalating game.

### ⚙️ One File to Balance the Whole Game: `game_config.py`

Every difficulty decision in this project — how forgiving a loss is, how fast the Minotaur moves, how quickly levels grow — should live in ONE settings file, not be scattered as hardcoded numbers across `minotaur_ai.py`, Blueprint graphs, and `editor_scripts.py`. This means a player who wants an easier game (or a much harder one) changes a handful of values in a single place, runs nothing but that one script again, and never has to touch Blueprint or hunt through other files at all.

```python
# game_config.py — one place to tune the entire game's difficulty
# Name:
# Date:

# --- What happens when the Minotaur catches the player? ---
# "restart_level" — respawn at the start of the CURRENT level, level counter unchanged
# "restart_game"  — send the player all the way back to Level 1
# "lose_a_life"   — track lives; restart_level while lives remain, then restart_game
RESET_MODE = "restart_level"
STARTING_LIVES = 3   # only used when RESET_MODE == "lose_a_life"

# --- Minotaur pathfinding & movement ---
RECALCULATE_INTERVAL = 0.5        # seconds between path recalculations — lower = more relentless
BASE_MINOTAUR_SPEED = 300.0        # Unreal units/second at Level 1
SPEED_INCREASE_PER_LEVEL = 25.0     # added to Minotaur speed each new level
NUMBER_OF_MINOTAURS = 1              # increase at higher levels for a different kind of harder

# --- Level generation & difficulty ramp ---
STARTING_WIDTH = 40
STARTING_HEIGHT = 30
WIDTH_GROWTH_PER_LEVEL = 10
HEIGHT_GROWTH_PER_LEVEL = 8

# --- Fairness ---
GRACE_PERIOD_SECONDS = 3.0   # Minotaur doesn't move for this long after a new level loads
CATCH_RADIUS = 100.0          # size of the "lose" trigger volume around the Minotaur


def get_minotaur_speed(level):
    """Speed scales UP with level — this is the single biggest difficulty lever."""
    return BASE_MINOTAUR_SPEED + (SPEED_INCREASE_PER_LEVEL * (level - 1))


def get_level_dimensions(level):
    """Each level's generate_rooms() call gets larger, using the growth rates above."""
    width = STARTING_WIDTH + (WIDTH_GROWTH_PER_LEVEL * (level - 1))
    height = STARTING_HEIGHT + (HEIGHT_GROWTH_PER_LEVEL * (level - 1))
    return width, height
```

The values under **Minotaur pathfinding & movement** and **Fairness** exist so Blueprint never needs a hardcoded number of its own — `minotaur_ai.py`'s exposed functions should read from `game_config` instead, the same way `next_level()` reads `get_level_dimensions()` instead of typing `width += 10` directly.

### 💡 Wiring `RESET_MODE` into the catch behaviour

Rather than have the lose-trigger's Blueprint graph decide what happens on a catch, expose ONE more Python function that makes that decision — keeping "Blueprint handles *when*, Python handles *what*" consistent with everything else this unit:

```python
# Add to minotaur_ai.py
import game_config

CURRENT_LIVES = game_config.STARTING_LIVES
CURRENT_LEVEL = 1

@unreal.uclass()
class GameManager(unreal.BlueprintFunctionLibrary):
    @unreal.ufunction(static=True, ret=str, meta=dict(Category="GameManager"))
    def handle_minotaur_catch():
        global CURRENT_LIVES, CURRENT_LEVEL

        if game_config.RESET_MODE == "restart_game":
            CURRENT_LEVEL = 1
            return "restart_game"

        elif game_config.RESET_MODE == "lose_a_life":
            CURRENT_LIVES -= 1
            if CURRENT_LIVES <= 0:
                CURRENT_LIVES = game_config.STARTING_LIVES
                CURRENT_LEVEL = 1
                return "restart_game"
            return "restart_level"

        else:   # "restart_level" — the default
            return "restart_level"
```

Blueprint's lose-trigger `On Component Begin Overlap` calls `Get Handle Minotaur Catch`, receives back a plain string (`"restart_level"` or `"restart_game"`), and branches on that string to decide where to respawn the player — Blueprint never needs to know WHY, only what to do.
