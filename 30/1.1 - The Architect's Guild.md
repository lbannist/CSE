## What Do These Words Actually Mean?

These terms get used loosely in conversation. Here is the precise meaning of each, because precision is what separates "it sort of works" from "I understand why it works":

| Term | Meaning | Example |
|---|---|---|
| **Inheritance** | A class receives the attributes and methods of a parent class | `Player(Entity)` — Player inherits everything Entity has |
| **`super()`** | Calls the parent class's version of a method — usually `__init__` | `super().__init__(name, health)` |
| **Overriding** | A subclass replaces a parent's method with its own version | `Boss` redefines `attack_target()` |
| **Abstract class** | A class that can never be instantiated directly — only inherited from | `Entity(ABC)` |
| **Abstract method** | A method an abstract class *requires* every subclass to implement | `@abstractmethod def attack_target(self)` |
| **Polymorphism** | Different object types respond correctly to the same method call | Looping over mixed `Entity` types and calling `.attack_target()` on each |
| **Encapsulation** | Protecting an object's internal data from being set to invalid values | `@property` guarding `health` |
| **Name-mangling** | Python renaming `__attr` to `_ClassName__attr` to discourage outside access | `self.__health` → `self._Entity__health` |
| **Dunder method** | A method with double underscores that plugs into Python's built-in behaviour | `__str__`, `__eq__`, `__len__` |

## Key Vocabulary

| Term | What it means |
|---|---|
| `super().__init__(...)` | Calls the parent class's constructor so you don't repeat its setup code |
| `abc.ABC` | Base class that makes a class abstract (cannot be instantiated) |
| `@abstractmethod` | Decorator marking a method that every subclass *must* implement |
| `@property` | Turns a method into something accessed like an attribute (`obj.health`, no parentheses) |
| `@x.setter` | Pairs with `@property` to control what happens when you *set* the value |
| `__str__` | Defines what `print(obj)` shows — friendly, for players/users |
| `__repr__` | Defines what shows in the console/debugger — precise, for developers |
| `__eq__` | Defines what `obj_a == obj_b` checks |
| `__lt__` | Defines what `obj_a < obj_b` checks — powers `.sort()` automatically |
| `__len__` | Defines what `len(obj)` returns |
| `__contains__` | Defines what `x in obj` checks |
| `__add__` | Defines what `obj_a + obj_b` does |

**Block 1 — Why repeating `__init__` is a problem:**

`BadPlayer` and `BadEnemy` below are two separate classes that were never told they're related — so they each write their own version of the same setup code. As you read it, look for exactly which lines are identical between the two classes, and ask yourself: if a third class needed the same three fields, would you copy them a third time?

```python
# sandbox_inheritance.py  — Block 1

# This is the WRONG way — two classes that duplicate almost everything
class BadPlayer:
    def __init__(self, name, health, attack):
        self.name   = name
        self.health = health
        self.attack = attack
        self.mana   = 30    # the only real difference

class BadEnemy:
    def __init__(self, name, health, attack):
        self.name   = name       # duplicated
        self.health = health     # duplicated
        self.attack = attack     # duplicated
        self.loot   = []         # the only real difference

# If you ever need to add a new shared stat (say, "level"),
# you now have to remember to add it in BOTH places.
# Forget one, and you have a silent bug.
p = BadPlayer("Alex", 100, 15)
e = BadEnemy("Goblin", 20, 5)
print(p.name, p.health, p.attack)
print(e.name, e.health, e.attack)
```

**Block 2 — Fixing it with inheritance and `super()`:**

Now `Entity` holds the shared setup code exactly once, and `Player`/`Enemy` each call `super().__init__()` instead of repeating it. Before you run this, predict: what do you think `alex.name` will equal, given that `Player` never sets `self.name` itself? Then run it and check.

```python
# sandbox_inheritance.py  — Block 2

class Entity:
    def __init__(self, name, health, attack):
        # This code now lives in ONE place
        self.name   = name
        self.health = health
        self.attack = attack

    def attack_target(self, target):
        target.health -= self.attack
        print(f"{self.name} attacks {target.name} for {self.attack} damage!")

    def is_alive(self):
        return self.health > 0


class Player(Entity):
    def __init__(self, name, health, attack, mana):
        # super().__init__(...) runs Entity's __init__ for us —
        # name, health, and attack get set WITHOUT us rewriting that code
        super().__init__(name, health, attack)
        self.mana = mana    # Player only adds what makes it DIFFERENT


class Enemy(Entity):
    def __init__(self, name, health, attack, loot_table):
        super().__init__(name, health, attack)
        self.loot_table = loot_table

    def drop_loot(self):
        return self.loot_table


alex   = Player("Alex", 100, 15, 30)
goblin = Enemy("Goblin", 20, 5, ["Gold Coin", "Rusty Dagger"])

print(alex.name, alex.health, alex.mana)      # Entity's fields + Player's own field
print(goblin.name, goblin.drop_loot())        # Entity's fields + Enemy's own method
```

Notice: if you add a new stat to `Entity.__init__`, **every subclass gets it automatically**. That's the whole point.

**Block 3 — Method overriding: same interface, different behaviour:**

`Boss` inherits from `Enemy` but rewrites `attack_target()` to hit harder. Both `goblin_from_block2` and `malachar` are called with the exact same line of code — `.attack_target(alex)` — so as you read the output, notice that the *code calling it* doesn't change at all; only the *object being called* determines what happens.

```python
# sandbox_inheritance.py  — Block 3

class Boss(Enemy):
    # Boss does NOT override __init__ — it's built exactly like any other Enemy
    # Boss DOES override attack_target — it fights differently
    def attack_target(self, target):
        print(f"{self.name} winds up a devastating strike!")
        target.health -= self.attack * 2     # bosses hit twice as hard

malachar = Boss("Malachar", 200, 20, ["Ancient Tome"])
alex     = Player("Alex", 100, 15, 30)

# Same method call, different behaviour, because Boss overrode it
goblin_from_block2 = Enemy("Goblin", 20, 5, [])
goblin_from_block2.attack_target(alex)   # uses Entity's version
malachar.attack_target(alex)             # uses Boss's OWN version
print(f"Alex health after both attacks: {alex.health}")
```

Run this and check: how much health did Alex lose to the goblin's attack vs. the boss's attack?

### 💡 Hints

**Deciding what belongs in `Entity` vs. a subclass — ask this question:**

> "Does *every* character in my game need this, or only some of them?"

If every character needs it (name, health, being alive or dead) → it belongs in `Entity`.
If only some need it (mana is only for spellcasters, loot is only for enemies) → it belongs in the subclass.

**The `super().__init__()` pattern, step by step:**

```python
class Player(Entity):
    def __init__(self, name, health, attack, mana):
        # Step 1: Call the parent's __init__ FIRST, passing along
        #         the arguments the parent actually needs
        super().__init__(name, health, attack)

        # Step 2: THEN set up whatever is unique to this subclass
        self.mana = mana
```

**A common mistake to avoid:**

```python
# WRONG — this skips Entity's __init__ entirely and duplicates its work
class Player(Entity):
    def __init__(self, name, health, attack, mana):
        self.name   = name      # duplicated from Entity
        self.health = health    # duplicated from Entity
        self.attack = attack    # duplicated from Entity
        self.mana   = mana
```

This *runs*, but it defeats the purpose of inheritance — if `Entity` ever changes how it sets up `health` (say, adding validation), `Player` won't get that change.

**Overriding `NPC.interact()` — the shape to follow:**

```python
class NPC(Entity):
    def __init__(self, name, health, dialogue):
        # Step 3: NPCs don't attack, so pass attack=0 up to Entity
        super().__init__(name, health, attack=0)
        self.dialogue = dialogue

    def interact(self, player):
        # Step 4: This OVERRIDES nothing yet — Entity doesn't have interact()
        #         But Player will ALSO define interact() differently — that's
        #         the polymorphism you'll use in Checkpoint 2
        print(f"{self.name}: {self.dialogue}")
```

**Block 2 — What happens with NO shared contract (the problem `abc` solves):**

`BrokenEnemy` was allowed to be created even though it never defines `attack_target()`. Watch closely for *when* the error actually happens — is it the moment `BrokenEnemy("Slime", 10)` is constructed, or only later when the loop tries to call the missing method?

```python
# sandbox_polymorphism.py  — Block 2

class Entity:
    def __init__(self, name, health):
        self.name   = name
        self.health = health
    # NOTE: no attack_target() defined here at all
```

**Block 3 — Enforcing the contract with `abc`:**

Same `BrokenEnemy` mistake as Block 2, but `Entity` now inherits from `ABC` and marks `attack_target()` with `@abstractmethod`. Watch for the moment the error now occurs — has it moved earlier or later compared to Block 2?

```python
# sandbox_polymorphism.py  — Block 3
from abc import ABC, abstractmethod

class Entity(ABC):
    def __init__(self, name, health):
        self.name   = name
        self.health = health

    @abstractmethod
    def attack_target(self, target):
        # No implementation needed here — this just DECLARES the requirement
        pass

    def is_alive(self):
        # Regular methods (no @abstractmethod) work exactly as normal
        # and are inherited as-is — this one does NOT need to be overridden
        return self.health > 0


class BrokenEnemy(Entity):
    pass    # still "forgot" attack_target()

# Try to create it:
try:
    goblin = BrokenEnemy("Slime", 10)
except TypeError as error:
    # Python refuses to create the object AT ALL — caught immediately,
    # at the moment of construction, not buried in some later gameplay bug
    print(f"Caught immediately: {error}")
```

Compare Block 2's error (an `AttributeError` deep inside gameplay) to Block 3's error (a `TypeError` the instant you try to build the broken object). Which would you rather debug at 11pm before an assignment is due?

### 💡 Hints

**Deciding what should be abstract vs. concrete:**

> Ask: "Does every subclass need its OWN version of this, or can they all share one version?"

`attack_target()` → every entity type fights differently → **abstract**
`is_alive()` → the logic (`health > 0`) is identical for everyone → **concrete** (regular method)

**The exact shape of an abstract class:**

```python
from abc import ABC, abstractmethod

class Entity(ABC):                    # Step A: inherit from ABC, not nothing
    def __init__(self, name, health):
        self.name   = name
        self.health = health

    @abstractmethod                     # Step B: mark the method as required
    def attack_target(self, target):
        pass                             # Step C: body can just be `pass`

    def is_alive(self):                 # Step D: no decorator — this is concrete
        return self.health > 0
```

**Does `NPC` need to fight?** Its `attack_target()` can be a no-op — it still needs to *exist*, since `abc` only checks that the method is *defined somewhere in the inheritance chain*, not that it does something dramatic:

```python
class NPC(Entity):
    def attack_target(self, target):
        pass    # NPCs satisfy the contract by doing nothing when "attacked"
```

**Block 3 — `@property`: controlling access properly:**

```python
        if value < 0:
            self.__health = 0                      # clamp to a valid floor
        elif value > self.max_health:
            self.__health = self.max_health         # clamp to a valid ceiling
        else:
            self.__health = value
```

## Checkpoint 4 — Dunder Methods: Making Objects Behave Like Python 🐍

### 📋 Your Task

Right now, `print(alex)` shows something like `<player.Player object at 0x7f...>` — completely useless. ### 🧠 Understand It First

**Block 1 — `__str__` vs `__repr__`:**

`Entity` (with no dunders) prints something unreadable, while `BetterEntity` prints something meaningful. As you read `BetterEntity`, compare the two return values in `__str__` and `__repr__` — they show almost the same information, so notice exactly what's different about *how* each one formats it, and who each format seems to be written for.

```python
# sandbox_dunders.py  — Block 1

class Entity:
    def __init__(self, name, health):
        self.name   = name
        self.health = health

goblin = Entity("Goblin", 20)
print(goblin)     # <__main__.Entity object at 0x7f9a2c...> — useless!
goblin            # same ugly output in a Python shell / debugger


class BetterEntity:
    def __init__(self, name, health):
        self.name   = name
        self.health = health

    def __str__(self):
        # Called by print() and str() — meant for PLAYERS/USERS to read
        return f"{self.name} ({self.health} HP)"

    def __repr__(self):
        # Called by the console/debugger — meant for DEVELOPERS to debug with
        # Convention: it should look like code that could recreate the object
        return f"Entity(name={self.name!r}, health={self.health})"

goblin2 = BetterEntity("Goblin", 20)
print(goblin2)     # Goblin (20 HP)                          <- __str__
goblin2            # Entity(name='Goblin', health=20)         <- __repr__
print(f"{goblin2!r}")   # forces __repr__ even inside an f-string
```

**Rule of thumb:** `__str__` is for players (friendly). `__repr__` is for developers debugging (precise, unambiguous, ideally looks like valid Python).

**Block 2 — Comparison dunders power sorting automatically:**

Notice that `party.sort()` is called with no extra arguments at all — no `key=`, nothing telling it *how* to sort. As you read `__lt__`, work out where `.sort()` is actually getting its sorting logic from, since it was never told directly.

```python
# sandbox_dunders.py  — Block 2

class Entity:
    def __init__(self, name, level):
        self.name  = name
        self.level = level

    def __repr__(self):
        return f"{self.name}(lvl {self.level})"

    def __eq__(self, other):
        # Called by:  entity_a == entity_b
        return self.level == other.level

    def __lt__(self, other):
        # Called by:  entity_a < entity_b
        # NOTE: you do NOT need to define __gt__ separately —
        # Python can figure out > by flipping < automatically in most contexts,
        # but list.sort() and sorted() ONLY need __lt__ to work completely.
        return self.level < other.level

alex     = Entity("Alex", 12)
malachar = Entity("Malachar", 20)
goblin   = Entity("Goblin", 3)

print(alex == goblin)              # False — uses __eq__
print(alex < malachar)             # True  — uses __lt__

party = [malachar, alex, goblin]
party.sort()                        # sort() uses __lt__ automatically — no key= needed!
print(party)                        # sorted lowest level to highest
```

**Block 3 — Container dunders: `__len__`, `__contains__`, `__add__`:**

`merged = bag1 + bag2` uses the same `+` symbol you've used on numbers your whole life. As you read `__add__`, pay attention to what it returns versus what it changes — then check the last two `print()` lines and notice that `bag1` still only has its original item, even after being "added." Why doesn't `+` change `bag1` itself?

```python
# sandbox_dunders.py  — Block 3

class Inventory:
    def __init__(self):
        self.items = []

    def add_item(self, name):
        self.items.append(name)

    def __len__(self):
        # Called by:  len(inventory)
        return len(self.items)

    def __contains__(self, item_name):
        # Called by:  item_name in inventory
        return item_name in self.items

    def __add__(self, other):
        # Called by:  inventory_a + inventory_b
        # Must RETURN a new object — this does not modify either original
        combined = Inventory()
        combined.items = self.items + other.items
        return combined

    def __repr__(self):
        return f"Inventory({self.items})"

bag1 = Inventory()
bag1.add_item("Iron Sword")
bag1.add_item("Health Potion")

bag2 = Inventory()
bag2.add_item("Shield")

print(len(bag1))                    # 2 — uses __len__
print("Iron Sword" in bag1)         # True — uses __contains__
print("Shield" in bag1)             # False — Shield is in bag2, not bag1

merged = bag1 + bag2                # uses __add__ — returns a BRAND NEW Inventory
print(merged)                       # Inventory(['Iron Sword', 'Health Potion', 'Shield'])
print(len(bag1))                    # still 2 — bag1 itself was NOT changed
```
