## What Do These Words Actually Mean?

| Term | Meaning | Example |
|---|---|---|
| **`*args`** | Collects any extra *positional* arguments into a tuple | `def f(*args): ...` then `f(1, 2, 3)` → `args = (1, 2, 3)` |
| **`**kwargs`** | Collects any extra *keyword* arguments into a dictionary | `def f(**kwargs): ...` then `f(x=1, y=2)` → `kwargs = {"x": 1, "y": 2}` |
| **Unpacking** | Spreading a list/dict back OUT into separate arguments when *calling* a function | `f(*my_list)`, `f(**my_dict)` |
| **Local scope** | Variables that only exist inside the function they were created in | A variable created inside `def f():` |
| **Enclosing scope** | A variable belonging to an outer function, visible to a nested function inside it | The variable a closure "remembers" |
| **Global scope** | Variables defined at the top level of a file, visible everywhere in that file | Something defined outside any function |
| **Closure** | A function that "remembers" variables from the scope it was created in, even after that outer scope has finished running | `make_counter()` returning an inner function |
| **Decorator** | A function that takes another function and returns a modified version of it | `@cooldown` above a function definition |
| **Decorator factory** | A function that *returns* a decorator, letting the decorator itself take arguments | `@cooldown(seconds=5)` |

---

## Key Vocabulary

| Term | What it means |
|---|---|
| `def f(*args)` | `args` becomes a tuple of every extra positional argument passed in |
| `def f(**kwargs)` | `kwargs` becomes a dict of every extra keyword argument passed in |
| `f(*my_list)` | Unpacks a list into separate positional arguments when calling `f` |
| `f(**my_dict)` | Unpacks a dict into separate keyword arguments when calling `f` |
| `global x` | Inside a function, explicitly says "use the global `x`, not a local one" |
| `nonlocal x` | Inside a nested function, says "use the enclosing function's `x`, not create a new local one" |
| `functools.wraps` | Decorator-writing helper that preserves the original function's name/docstring |
| `@staticmethod` | Marks a method that doesn't need `self` at all — just lives inside the class for organisation |
| `@classmethod` | Marks a method that receives the class itself (`cls`) instead of an instance — often used as an alternate constructor |

**Block 3 — `**kwargs`: any combination of named effects, plus unpacking:**

`**kwargs` does the same thing but for keyword arguments, collecting them into a dictionary. The last few lines also show **unpacking** — using `*` or `**` when *calling* a function to spread a list or dict back out into separate arguments. Trace carefully: `effects` inside the function and `my_effects` outside it end up holding the same data, but arrive there in opposite directions.

```python
# sandbox_args_kwargs.py  — Block 3

def cast_on_any(caster, *targets, **effects):
    print(f"{caster} casts a spell on {len(targets)} target(s) with effects: {effects}")
    for name, amount in effects.items():
        print(f"  applies {name}: {amount}")

cast_on_any("Alex", "Goblin", "Slime", burn=5, slow=2)
# targets = ("Goblin", "Slime")
# effects = {"burn": 5, "slow": 2}

# UNPACKING — spreading data structures back into arguments at the call site:
my_target_list = ["Goblin", "Slime", "Orc"]
my_effects     = {"burn": 5, "freeze": 3}

cast_on_any("Alex", *my_target_list, **my_effects)
# * spreads the list into separate positional args
# ** spreads the dict into separate keyword args
# This line is EQUIVALENT to:
# cast_on_any("Alex", "Goblin", "Slime", "Orc", burn=5, freeze=3)
```

## Checkpoint 2 — Scope & Closures 🔐

### 📋 Your Task

This checkpoint has no game features to add yet — it exists to teach you exactly what you need to understand decorators in Checkpoint 3. A decorator is fundamentally a closure, so if closures don't make sense, decorators will feel like magic instead of a tool you understand. Take this one slowly.

### 🧠 Understand It First

Create `sandbox_scope.py`.

**Block 1 — Local vs. global scope:**

A variable created inside a function only exists inside that function — it does not "leak out." As you run this, predict the final printed value of the global `gold` *before* you scroll down to check.

```python
# sandbox_scope.py  — Block 1

gold = 100   # this is a GLOBAL variable — defined outside any function

def spend_gold():
    gold = 0   # this creates a NEW LOCAL variable called gold — it does NOT
               # touch the global one, even though the name is identical!
    print(f"Inside the function, gold = {gold}")

spend_gold()
print(f"Outside the function, gold = {gold}")   # still 100 — untouched!
```

**Block 2 — Changing a global on purpose with the `global` keyword:**

Sometimes you *do* want a function to change a global variable. Python requires you to say so explicitly with the `global` keyword — otherwise, as Block 1 showed, it just creates a new local variable instead.

```python
# sandbox_scope.py  — Block 2

gold = 100

def spend_gold_properly(amount):
    global gold          # explicitly says: "use the GLOBAL gold, don't make a local one"
    gold -= amount        # this now actually changes the global variable

spend_gold_properly(30)
print(f"Gold after spending: {gold}")   # 70 — actually changed this time
```

**Block 3 — Enclosing scope and closures: a function that remembers:**

`make_buff_tracker()` returns an *inner* function, and that inner function keeps access to `buff_amount` even after `make_buff_tracker()` has already finished running. This is the "magic" part — read it slowly and notice that `tracker` is called with no arguments at all, yet it still knows what `buff_amount` was.

```python
# sandbox_scope.py  — Block 3

def make_buff_tracker(buff_amount):
    total_applied = 0   # this belongs to the ENCLOSING scope, not global, not local-only

    def apply_buff():
        nonlocal total_applied     # says: "use the ENCLOSING total_applied, don't
                                    # create a new local one" — the counterpart to `global`
        total_applied += buff_amount
        print(f"Buff applied! Total applied so far: {total_applied}")

    return apply_buff   # NOTE: we return the FUNCTION itself, not the result of calling it

# make_buff_tracker(5) runs once, sets buff_amount=5, and returns the inner function
speed_tracker = make_buff_tracker(5)

speed_tracker()   # Total applied so far: 5
speed_tracker()   # Total applied so far: 10
speed_tracker()   # Total applied so far: 15
# Every call "remembers" buff_amount and total_applied from when it was created —
# this remembered environment is called a CLOSURE
```

**Why does `nonlocal` even matter here? Try it WITHOUT `nonlocal` first:**

```python
def make_counter():
    count = 0
    def increment():
        count += 1    # this LOOKS like it should work, but...
        return count
    return increment

counter()   # UnboundLocalError! Without `nonlocal`, `count += 1` tries to create
            # a brand new LOCAL `count` inside increment() — but it also tries
            # to READ count on the right side of += before it's been assigned locally
```

Adding `nonlocal count` right after `def increment():` fixes this by telling Python to use the enclosing `count`, not create a new local one.

**Building `make_cooldown_tracker` — think in terms of "remembered state":**

```python
import time

def make_cooldown_tracker(cooldown_seconds):
    last_call_time = 0    # Step A: this variable belongs to the ENCLOSING scope

    def ready_to_fire():
        nonlocal last_call_time   # Step B: needed because we're about to REASSIGN it
        now = time.time()
        if now - last_call_time >= cooldown_seconds:
            last_call_time = now   # Step C: update the remembered time
            return True
        return False

    return ready_to_fire   # Step D: return the function itself, don't call it here
```

## Checkpoint 3 — Writing Custom Decorators ⚗️

### 📋 Your Task

Now that closures make sense, decorators are just closures with a specific job: wrapping a function to add behaviour before/after it runs, without changing the function's own code. This checkpoint builds `@cooldown` and `@requires_mana` — real decorators you'll apply directly to `cast_spell`.

### 🧠 Understand It First

Create `sandbox_decorators.py`.

**Block 1 — The simplest possible decorator:**

A decorator is a function that takes a function and returns a new function. `@shout` below is just shorthand for `speak = shout(speak)` — as you read it, find the exact line where that substitution actually happens.

```python
# sandbox_decorators.py  — Block 1

def shout(func):
    def wrapper():
        result = func()               # call the ORIGINAL function
        return result.upper()          # then modify what it returned
    return wrapper                     # return the NEW function

def speak():
    return "hello, traveler"

speak = shout(speak)   # manually "decorating" — this is what @shout does automatically
print(speak())          # HELLO, TRAVELER

# The @ symbol below is EXACTLY equivalent to the line above:
@shout
def greet():
    return "welcome to the kingdom"

print(greet())   # WELCOME TO THE KINGDOM
```

**Block 2 — Passing arguments through with `*args`/`**kwargs`, and why `functools.wraps` matters:**

Real functions take arguments, so `wrapper` needs to accept and forward them. Notice how `*args`/`**kwargs` from Checkpoint 1 come back here for a completely different purpose — letting a decorator work on ANY function, regardless of what parameters it takes.

```python
# sandbox_decorators.py  — Block 2

import functools

def log_call(func):
    @functools.wraps(func)     # preserves func's original name/docstring — try
                                 # commenting this out and checking add.__name__ after
    def wrapper(*args, **kwargs):
        print(f"Calling {func.__name__} with args={args}, kwargs={kwargs}")
        result = func(*args, **kwargs)    # forward everything through
        print(f"{func.__name__} returned {result}")
        return result
    return wrapper

@log_call
def add(a, b):
    return a + b

print(add(3, 4))
print(f"Function name is still: {add.__name__}")   # "add", not "wrapper" — thanks to functools.wraps
```

**Block 3 — A decorator FACTORY: a decorator that takes its own arguments:**

`@cooldown` needs to know HOW LONG the cooldown is — but a decorator normally only receives the function it's decorating, nothing else. The fix is an extra layer: a function that takes the cooldown length and *returns* the actual decorator. This directly reuses the closure pattern from Checkpoint 2.

```python
# sandbox_decorators.py  — Block 3

import time
import functools

def cooldown(seconds):
    # This OUTER function takes the decorator's OWN argument (seconds)
    # and returns the ACTUAL decorator
    def decorator(func):
        last_call_time = 0    # remembered state, exactly like Checkpoint 2

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            nonlocal last_call_time
            now = time.time()
            if now - last_call_time < seconds:
                print(f"{func.__name__} is still on cooldown!")
                return None
            last_call_time = now
            return func(*args, **kwargs)
        return wrapper
    return decorator

@cooldown(seconds=2)
def fireball():
    print("🔥 Fireball cast!")

fireball()   # fires
fireball()   # blocked — still on cooldown
time.sleep(2)
fireball()   # fires again
```

Compare this to `make_cooldown_tracker` from Checkpoint 2 — same idea, wrapped around a function instead of returned as a standalone check.

### 💡 Hints

**Why `requires_mana` needs access to `self`, and why that's different from Block 3's example:**

`cast_spell(self, *targets, **effects)` is a *method* — its first argument is always `self`. Your decorator's `wrapper(*args, **kwargs)` will receive `self` as `args[0]`:

```python
def requires_mana(amount):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(self, *args, **kwargs):
            # self is available here directly, since we named it explicitly
            if self.mana < amount:
                print(f"Not enough mana! Need {amount}, have {self.mana}.")
                return None
            self.mana -= amount
            return func(self, *args, **kwargs)   # pass self along too
        return wrapper
    return decorator
```

**Stacking two decorators — order matters, read from the BOTTOM up:**

```python
@cooldown(seconds=1)          # runs SECOND (outer check)
@requires_mana(amount=10)      # runs FIRST (inner check, closest to the function)
def cast_spell(self, *targets, **effects):
    ...

# When you call alex.cast_spell(...):
# 1. cooldown's wrapper runs first (it's the outermost layer)
# 2. IF cooldown allows it, requires_mana's wrapper runs next
# 3. IF mana allows it, the real cast_spell finally runs
```

Think of decorators stacked like this as layers of an onion — the one closest to `def` wraps the actual function first, and each decorator above it wraps the *previous* wrapped version.

## Checkpoint 4 — Built-in Decorators Revisited: `@staticmethod` & `@classmethod` 🏺

### 📋 Your Task

You've been using `@property` since Unit 1 without necessarily thinking of it as "a decorator" — it is one. This checkpoint introduces two more built-in decorators that don't wrap behaviour the way `@cooldown` does, but instead change *what a method receives* when it's called: `@staticmethod` (receives nothing extra at all) and `@classmethod` (receives the class itself instead of an instance).

### 🧠 Understand It First

Create `sandbox_builtin_decorators.py`.

**Block 1 — `@staticmethod`: a method that doesn't need `self`:**

Some functions logically belong inside a class for organisation, but never actually use `self` or any instance data. As you read this, notice that `Entity.calculate_damage_multiplier(...)` is called on the CLASS itself, not on any particular entity — there's no `self` anywhere in sight.

```python
# sandbox_builtin_decorators.py  — Block 1

class Entity:
    @staticmethod
    def calculate_damage_multiplier(attacker_level, defender_level):
        # NOTE: no "self" parameter at all — this method doesn't need
        # any particular instance's data to do its job
        level_gap = attacker_level - defender_level
        return max(1.0, 1.0 + (level_gap * 0.1))

# Called directly on the CLASS — no instance required
multiplier = Entity.calculate_damage_multiplier(10, 5)
print(f"Damage multiplier: {multiplier}")

# It ALSO works called on an instance, but still ignores that instance entirely
goblin = Entity()
print(goblin.calculate_damage_multiplier(3, 8))
```

**Block 2 — `@classmethod`: an alternate constructor:**

A classmethod receives the class itself (conventionally named `cls`) instead of an instance. This makes it perfect for writing alternate ways to build an object — here, building an `Entity` straight from a dictionary of save data instead of listing arguments one by one.

```python
# sandbox_builtin_decorators.py  — Block 2

class Entity:
    def __init__(self, name, health):
        self.name   = name
        self.health = health

    @classmethod
    def from_save_data(cls, data_dict):
        # cls IS the Entity class itself — calling cls(...) is the same
        # as calling Entity(...), but works correctly even for subclasses
        return cls(data_dict["name"], data_dict["health"])

    def __repr__(self):
        return f"Entity({self.name!r}, {self.health})"

save_data = {"name": "Goblin", "health": 20}

# The NORMAL way to build an Entity:
goblin_normal = Entity("Goblin", 20)

# The ALTERNATE way, using the classmethod:
goblin_from_save = Entity.from_save_data(save_data)

print(goblin_normal)
print(goblin_from_save)
```

**Block 3 — `@property` was a decorator all along, and stacking order matters:**

You've written `@property` and `@x.setter` since Unit 1. Now that you understand decorators are just functions that transform other functions, re-read your own `entity.py` from Unit 1 with that lens. Below, notice that `@classmethod` and `@staticmethod` can live in the exact same class as your custom `@cooldown`/`@requires_mana` — Python doesn't treat built-in and custom decorators any differently.

```python
# sandbox_builtin_decorators.py  — Block 3

class Entity:
    def __init__(self, name, health, max_health):
        self.name       = name
        self.max_health = max_health
        self.__health   = health

    @property                  # <- this IS a decorator, just like @cooldown
    def health(self):
        return self.__health

    @health.setter              # <- so is this
    def health(self, value):
        self.__health = max(0, min(value, self.max_health))

    @staticmethod
    def calculate_damage_multiplier(attacker_level, defender_level):
        return max(1.0, 1.0 + (attacker_level - defender_level) * 0.1)

    @classmethod
    def from_save_data(cls, data_dict):
        return cls(data_dict["name"], data_dict["health"], data_dict["max_health"])

# All three decorator STYLES coexist in one class:
goblin = Entity.from_save_data({"name": "Goblin", "health": 20, "max_health": 20})
goblin.health -= 500                     # @property setter clamps this
print(goblin.health)                       # 0, not negative
print(Entity.calculate_damage_multiplier(10, 5))   # @staticmethod, no instance needed
```
