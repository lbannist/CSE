## Why Are We Doing This?

Every loop you've written so far — `for`, `while` — solves a problem by repeating a block of code with some kind of counter or condition tracking progress. That's **iteration**, and it's usually the right tool. But some problems are naturally defined in terms of *smaller versions of themselves*: a maze is solved by solving the smaller maze that remains after your first step; a folder's total size is the sum of its files plus the total size of each folder inside it (which is the same problem, just smaller). Forcing these into a loop with manual bookkeeping is possible, but often much harder to read than just letting the problem solve itself, layer by layer. That's **recursion**.

This unit is about knowing both tools well enough to choose correctly — and about understanding *why* a recursive function that looks like only 4 lines of code can still crash your program if you get one detail wrong. It ends with something new: a monster that uses that same recursion, live, to hunt.

By the end of this unit you will:

- Be able to trace exactly what a recursive function does, step by step, including where it lives on the call stack
- Know why every recursive function needs a base case, and what happens if it doesn't have one
- Be able to solve the same problem both iteratively and recursively, and explain the trade-offs
- Build a recursive backtracking maze solver — and a recursive dungeon generator to go with it

- Understand memoization, and why it helps some recursive problems (Fibonacci) but not others (a target that keeps moving)

## What Do These Words Actually Mean?

| Term | Meaning | Example |
|---|---|---|
| **Iteration** | Repeating a block of code using a loop, tracked with a counter or condition | `for`, `while` |
| **Recursion** | A function that calls itself with a smaller version of the same problem | `factorial(n)` calling `factorial(n-1)` |
| **Base case** | The smallest version of the problem, solved directly with no further recursive call | `factorial(0)` returns `1` immediately |
| **Recursive case** | The part of the function that calls itself with a smaller input, moving toward the base case | `return n * factorial(n - 1)` |
| **Call stack** | The record Python keeps of every function call currently "in progress," waiting for the one it called to finish | Each recursive call adds a new layer |
| **Stack overflow / `RecursionError`** | What happens when recursive calls never reach a base case, and the call stack runs out of room | Missing or unreachable base case |
| **Backtracking** | Trying a path, and if it fails, undoing that choice and trying a different one | Maze solving |
| **Pathfinding** | Computing a route from one position to another through an environment | The Minotaur finding its way to the player |
| **Memoization** | Caching the result of a function call so repeated calls with the same input don't redo the work | A dictionary mapping input → already-computed output |

---

## Key Vocabulary

| Term | What it means |
|---|---|
| Base case | The condition that stops recursion — without one, the function calls itself forever |
| Recursive case | The part of the function where it calls itself, with an input that's closer to the base case |
| Call stack | Python's internal list of "currently running, waiting on something else" function calls |
| `RecursionError` | Python's error when the call stack gets too deep (default limit is 1000 calls) |
| Backtracking | Undoing a choice and trying another when the current path leads to a dead end |
| Pathfinding | Finding a route between two points, often re-run whenever one of those points changes |
| Memoization | Storing already-computed results so they don't need to be recalculated |
| `functools.lru_cache` | A built-in decorator that automatically memoizes a function's return values |

**Block 2 — Factorial, the recursive way:**

There's no loop here at all — the function calls *itself*. As you read it, find the **base case** (the condition where it stops calling itself) and the **recursive case** (where it calls itself again). Then, before running it, try to predict by hand what `factorial_recursive(3)` will return.

```python
# sandbox_recursion_basics.py  — Block 2

def factorial_recursive(n):
    if n == 0:                          # BASE CASE — the smallest version, solved directly
        return 1
    return n * factorial_recursive(n - 1)   # RECURSIVE CASE — calls itself with a smaller n

print(factorial_recursive(5))   # should match Block 1's answer: 120

# Add print statements to SEE the recursion happening:
def factorial_traced(n, depth=0):
    indent = "  " * depth
    print(f"{indent}factorial_traced({n}) called")
    if n == 0:
        print(f"{indent}base case hit, returning 1")
        return 1
    result = n * factorial_traced(n - 1, depth + 1)
    print(f"{indent}factorial_traced({n}) returning {result}")
    return result

factorial_traced(4)
```

Run the traced version and read the indented output top to bottom. Notice that the function calls itself all the way DOWN to the base case *before* any multiplication happens — the actual math only happens on the way back UP.

**Block 3 — What happens with NO base case:**

This function has a recursive case but never reaches a stopping point. As you run it (or read the error if you don't want to wait), notice the shape of the error message — specifically, what does Python call this kind of failure, and what number does it mention?

```python
# sandbox_recursion_basics.py  — Block 3

def broken_countdown(n):
    print(n)
    return broken_countdown(n - 1)   # no base case — n never stops decreasing!

try:
    broken_countdown(5)
except RecursionError as error:
    print(f"\nCaught it: {error}")
    print("Python's call stack has a default limit — every recursive call that")
    print("hasn't returned yet takes up space on that stack. With no base case,")
    print("this function would call itself forever, so Python stops it.")
```

### 💡 Hints

**Every recursive function needs to answer two questions:**

> 1. "What's the smallest version of this problem I can solve directly?" → your base case
> 2. "How does a bigger version of this problem relate to a smaller one?" → your recursive case

**Applying this to `sum_to_n_recursive`:**

```python
def sum_to_n_recursive(n):
    # Smallest version: sum_to_n_recursive(1) is just 1 — no further recursion needed
    if n == 1:
        return 1
    # Bigger version: the sum from 1 to n is n PLUS the sum from 1 to (n - 1)
    return n + sum_to_n_recursive(n - 1)
```

**A common mistake — forgetting the base case is checked FIRST:**

```python
# WRONG ORDER — this never gets a chance to check the base case in some cases
def broken(n):
    result = n + broken(n - 1)   # recursive call happens before any check!
    if n == 1:
        return 1
    return result
```

Always check the base case at the very top of the function, before any recursive call is made.

**Block 1 — Recursive Fibonacci, and why it gets slow fast:**

Fibonacci's recursive case calls itself *twice*, not once — as you read it, think about how many total function calls that means for `fib(10)` versus `fib(5)`, and why doubling the input doesn't just double the work.

```python
for i in range(10):
```

**Block 3 — Recursive traversal of the labyrinth's chamber map:**

Dictionaries can contain other dictionaries, to any depth, and you don't know in advance how deep any particular branch goes. As you read `explore_dungeon`, notice the two different things it does depending on what it finds: a `str` (an item, print it directly) or a `dict` (a chamber with more chambers inside, recurse into it).

```python
# sandbox_classic_recursion.py  — Block 3

dungeon_map = {
    "Entry Hall": {
        "Armory": "Iron Sword",
        "Guard Room": {
            "Hidden Vault": "Ancient Tome",
        },
    },
    "West Wing": {
        "Library": "Spellbook",
    },
}

def explore_dungeon(rooms, depth=0):
    indent = "  " * depth
    for room_name, contents in rooms.items():
        print(f"{indent}{room_name}")
        if isinstance(contents, dict):
            # It's a chamber containing MORE chambers — recurse into it
            explore_dungeon(contents, depth + 1)
        else:
            # It's an item — this is effectively a base case for this BRANCH
            print(f"{indent}  contains: {contents}")

explore_dungeon(dungeon_map)
```

Notice there isn't one single "base case" the way there was for factorial — instead, each branch of the dictionary stops recursing the moment it hits something that ISN'T another dictionary.

**`count_items` — the base case is "this isn't a dict anymore":**

```python
def count_items(rooms):
    total = 0
    for room_name, contents in rooms.items():
        if isinstance(contents, dict):
            total += count_items(contents)    # recurse, add whatever it finds
        else:
            total += 1                          # base case for this branch: found an item
    return total
```

**`find_item` — recursion that can stop EARLY once it finds an answer:**

```python
def find_item(rooms, item_name):
    for room_name, contents in rooms.items():
        if isinstance(contents, dict):
            result = find_item(contents, item_name)   # search inside this room
            if result is not None:
                return result                            # found it — stop searching, return immediately
        else:
            if contents == item_name:
                return room_name                          # found it at THIS level
    return None   # searched everything at this level and found nothing
```

## Checkpoint 3 — Recursive Backtracking & the Minotaur's Pathfinding 🐂

### 📋 Your Task

Then you'll **generalize it** so it can path toward *any* coordinate, not just a hardcoded exit — because a monster chasing a player needs to path toward wherever the player currently is, and that changes every turn. ### 🧠 Understand It First

Create `sandbox_backtracking.py`.

**Block 1 — Representing a maze, and the shape of a backtracking solver:**

The maze below is just a grid of characters — `#` for walls, `.` for open floor, `S` for start, `E` for exit. As you read `solve_maze`, pay close attention to the order of the four things it does at each cell: mark it visited, check if it's the exit, try each direction recursively, and — this is the key part — **unmark it if none of those directions worked**.

```python
# sandbox_backtracking.py  — Block 1

maze = [
    "S.#....",
    "..#.##.",
    "....#..",
    "##.##.#",
    "....#.E",
]

def solve_maze(maze, row, col, visited=None, path=None):
    if visited is None:
        visited = set()
    if path is None:
        path = []

    # Out of bounds or hit a wall — this branch is a dead end
    if row < 0 or row >= len(maze) or col < 0 or col >= len(maze[0]):
        return None
    if maze[row][col] == "#":
        return None
    if (row, col) in visited:
        return None   # already tried this cell on this path — don't loop forever

    visited.add((row, col))
    path.append((row, col))

    if maze[row][col] == "E":
        return path[:]   # FOUND IT — return a copy of the path that got us here

    # Try all four directions, recursively, from this cell
    for delta_row, delta_col in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
        result = solve_maze(maze, row + delta_row, col + delta_col, visited, path)
        if result is not None:
            return result   # a direction worked — pass the successful path back up

    # NONE of the four directions worked from here — this is the BACKTRACK step
    path.pop()
    return None

start_row, start_col = 0, 0
solution = solve_maze(maze, start_row, start_col)
print(f"Solution path: {solution}")
```

```python
def solve_maze_traced(maze, row, col, visited=None, path=None, depth=0):
    if visited is None:
        visited = set()
    if path is None:
        path = []
    indent = "  " * depth

    if row < 0 or row >= len(maze) or col < 0 or col >= len(maze[0]) or maze[row][col] == "#":
        return None
    if (row, col) in visited:
        return None

    visited.add((row, col))
    path.append((row, col))
    print(f"{indent}Visiting ({row},{col})")

    if maze[row][col] == "E":
        print(f"{indent}Found the exit!")
        return path[:]

    for delta_row, delta_col in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
        result = solve_maze_traced(maze, row + delta_row, col + delta_col, visited, path, depth + 1)
        if result is not None:
            return result

    print(f"{indent}Dead end at ({row},{col}) — backtracking")
    path.pop()
    return None
```

**Block 3 — Generalizing: pathfinding toward ANY coordinate, not just `"E"`:**

`solve_maze` only ever looks for the character `"E"`. But the Minotaur needs to path toward the *player*, and the player moves every turn — there's no fixed symbol to search for. `find_path` below fixes this by taking a target **coordinate** instead of relying on a symbol at all. As you compare it to Block 1, find the ONE check that changed, and notice that `solve_maze` can now be rewritten as just a special case of `find_path`.

```python
# sandbox_backtracking.py  — Block 3

def find_path(maze, start, target, visited=None, path=None):
    row, col = start
    if visited is None:
        visited = set()
    if path is None:
        path = []

    if row < 0 or row >= len(maze) or col < 0 or col >= len(maze[0]) or maze[row][col] == "#":
        return None
    if (row, col) in visited:
        return None

    visited.add((row, col))
    path.append((row, col))

    if (row, col) == target:              # <-- the ONLY real change from Block 1:
        return path[:]                     #     comparing to a COORDINATE, not a symbol

    for delta_row, delta_col in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
        result = find_path(maze, (row + delta_row, col + delta_col), target, visited, path)
        if result is not None:
            return result

    path.pop()
    return None

# solve_maze can now be built ON TOP of find_path — locate "E" in the grid first,
# then just call find_path toward that coordinate:
def solve_maze(maze, start):
    for r, row_string in enumerate(maze):
        for c, char in enumerate(row_string):
            if char == "E":
                return find_path(maze, start, (r, c))
    return None   # no exit found in the maze at all

print(solve_maze(maze, (0, 0)))
print(find_path(maze, (0, 0), (2, 4)))   # paths to ANY coordinate, not just the exit
```

This is the exact tool the Minotaur needs: `find_path(maze, minotaur_position, player_position)`, recalculated fresh every turn, since `player_position` keeps changing.

### 💡 Hints

**Why `visited` prevents infinite loops:**

Without tracking visited cells, the solver could walk back and forth between two open cells forever (right, then left, then right again...). Marking a cell as visited before recursing means the solver will never try that exact cell twice **along the same path** — this is essential, not optional.

**The difference between `find_path` (stop at first solution) and `find_all_paths` (collect every solution):**

```python
def find_all_paths(maze, start, target, visited=None, path=None, all_solutions=None):
    row, col = start
    if all_solutions is None:
        all_solutions = []
    # ... same setup and dead-end checks as find_path ...

    if (row, col) == target:
        all_solutions.append(path[:])   # RECORD this solution...
        # ...but do NOT return early! Keep exploring other directions from here
    else:
        for delta_row, delta_col in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
            find_all_paths(maze, (row + delta_row, col + delta_col), target, visited, path, all_solutions)

    path.pop()                     # backtrack regardless of whether this branch found the target
    visited.discard((row, col))    # allow OTHER paths to revisit this cell later
    return all_solutions
```

Notice `find_all_paths` needs `visited.discard(...)` — undoing the visited-marking too — because a cell that's a dead end on one path might be part of a different valid path explored later from a different branch.

## Checkpoint 4 — Memoization: Making Recursion Fast 🚀

### 📋 Your Task

Checkpoint 2 showed that `fib_recursive` gets painfully slow as `n` grows, because it recalculates the same smaller Fibonacci values over and over. This checkpoint fixes that using **memoization** — caching results so repeated work is never redone — first by hand, then using a built-in decorator that does it automatically. This connects directly back to Unit 2: `@lru_cache` is a decorator, exactly like `@cooldown`.

**Block 2 — Memoizing by hand with a dictionary:**

The exact same recursive structure as before, but with one addition: check the cache first, and store the result before returning. As you compare this to Block 1, find the ONE new `if` statement and the ONE new line that make all the difference.

```python
# sandbox_memoization.py  — Block 2

def fib_memoized(n, cache=None):
    if cache is None:
        cache = {}
    if n in cache:
        return cache[n]      # already computed — skip the recursion entirely
    if n <= 1:
        return n
    result = fib_memoized(n - 1, cache) + fib_memoized(n - 2, cache)
    cache[n] = result          # store it before returning, for next time
    return result

import time

print(f"Memoized fib(35) took {time.time() - start:.5f} seconds")

# it would take multiple SECONDS. This should be nearly instant.
```

```python
# called with a DIFFERENT target_position almost every single turn, because the
```

### 💡 Hints

**Why `cache=None` as a default, instead of `cache={}` directly:**

```python
# DANGEROUS — mutable default arguments are shared across EVERY call, forever,
# because Python only creates the default dict ONCE, when the function is defined
def fib_memoized(n, cache={}):
    ...

# SAFE — a new empty dict is created fresh, every time cache isn't explicitly passed
def fib_memoized(n, cache=None):
    if cache is None:
        cache = {}
    ...
```

**Why `@lru_cache` can't be used directly on `count_items(rooms)` from Checkpoint 2, either:**

`lru_cache` needs its cache KEY (the function's arguments) to be hashable — usable as a dictionary key. Dictionaries themselves are NOT hashable (they can change, so Python won't allow it):

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def count_items(rooms):   # rooms is a dict
    ...

count_items(dungeon_map)   # TypeError: unhashable type: 'dict'
```

This is a real, common limitation — memoization works great for functions whose inputs are numbers, strings, or tuples, but needs extra care for anything built on dictionaries or lists, and provides ZERO benefit for functions like the Minotaur's, where the input is expected to be different nearly every time it's called.
